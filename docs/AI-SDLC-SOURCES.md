# Summary of public sources on AI-SDLC models

Captured 10 Oct 2026. A summary of the public documentation the scripted AI-SDLC scenes paraphrase. Convention: text with no mark or in quotes comes from the source. Text marked **[Synthesis]** is my reading, not the source's.

## 1. AWS: AI-Driven Development Life Cycle (AI-DLC)

**Who and when.** Raja SP, Principal Solutions Architect at AWS, in the AWS DevOps & Developer Productivity Blog, **31 Jul 2025**. It is a short text (~1,500 words) and a positioning piece. The «AI-DLC white paper» it links to (`prod.d13rzhkk8cj2z0.amplifyapp.com`) is a JavaScript app that **could not be read** with a direct download.

**Phases (exact names).** **Inception phase**, **Construction phase** and **Operations phase**. Each phase leaves more context for the next one.
- Inception: «AI transforms business intent into detailed requirements, stories and units through "Mob Elaboration"».
- Construction: «AI proposes a logical architecture, domain models, code solution and tests through "Mob Construction"».
- Operations: «AI applies the accumulated context … to manage infrastructure as code and deployments, with team oversight».
- Its own vocabulary: *sprints* become **bolts** («measured in hours or days») and *Epics* become **Units of Work**.

**Roles.** The blog does not define formal roles.
- Humans it mentions: «product owners, developers, architects» (in the diagnosis and in the benefits), «cross functional team members» (image caption) and «the entire team» / «the team» in the *mob* rituals.
- AI appears as «central collaborator and teammate». The blog does not name agents.

**Artifacts.** «plans, requirements, and design artifacts» saved «to your project repository»; «requirements, stories, designs, code, and tests». For implementation it points to «Amazon Q Developer rules» and to «Kiro custom workflows» (the link goes to Kiro's steering page).

**Human / approval.** The base pattern: AI plans, asks, and then «implements solutions only after receiving human validation». AI «defers critical decisions to humans».

**After generating code.** The blog does not talk about CI/CD, gates or fitness functions. The closest it gets: «AI enhances quality by consistently applying organization-specific standards – your coding practices, design patterns, and security requirements – while generating comprehensive test suites». **[Synthesis]** This is control *before* generating (context) plus tests generated by the same AI. There is no deterministic architecture check.

**Useful quotes.**
- «AI creates a plan, asks clarifying questions to seek context, and implements solutions only after receiving human validation»
- «only humans possess the contextual understanding and knowledge of business requirements needed to make informed choices»
- «Traditional 'sprints' are replaced by 'bolts'»

### 1b. Complementary: `awslabs/aidlc-workflows` (the open-source implementation of AI-DLC)

I include it because this is where AI-DLC does define roles and gates.
- An AWS Labs repo, created 13 Nov 2025, version 2.11.0, MIT-0 license.
- It runs on Claude Code, Kiro CLI/IDE, Codex CLI, Cursor, opencode and GitHub Copilot.

**Phases and scale (README).** «5 phases and 33 stages from initialization through operation», «14 agents: 11 domain experts, 2 reviewers, and an adaptive composer», «Human approval gates and source-bound review evidence» and «The same deterministic engine across every supported harness».

**Agents (exact `display_name` and role according to their front-matter).**

| Agent | Declared role |
|---|---|
| Product Agent | product manager / business analyst. Leads Intent Capture, Market Research, Scope Definition, Requirements Analysis and User Stories |
| Product Lead | reviewer: «Does not produce — only reviews and challenges. Represents the customer's voice at the quality gate» |
| Design Agent | UX/UI |
| Architect Agent | «Solutions architect responsible for domain design, contract design, NFR patterns, and component decomposition» |
| Architecture Reviewer | reviewer: «reviews technical design artifacts for soundness, implementability, and coherence» |
| AWS Platform Agent | AWS infrastructure |
| Compliance Agent | GRC |
| Developer Agent | code generation and reverse engineering |
| Quality Agent | «QA lead … test strategy, test case design, quality gates». Leads Build and Test |
| DevSecOps Agent | security |
| Pipeline & Deploy Agent | «CI/CD engineer and release manager». Leads CI Pipeline and Deployment Pipeline |
| Delivery Agent | «Engineering manager responsible for team formation, Bolt sequencing, and phase handoffs» |
| Operations Agent | SRE |
| Composer Agent | composes the minimal flow |

**After generating.** The knowledge file of the Pipeline & Deploy Agent (`cicd-patterns.md`) lists these «Quality Gates»: Lint, Test coverage (≥80%), Security scan, Integration tests, «Manual approval — Tech lead or product owner sign-off» and Smoke tests. **[Synthesis]** It includes no architecture-rule gate. Architecture is left to an LLM reviewer (Architecture Reviewer).

**Multi-repo.** For polyrepo: «Simpler per-repo but harder to coordinate cross-service changes. Use contract testing (Pact) to verify compatibility across repos». The Composer marks «multi-repo = HIGH CSU baseline» (CSU = code structural uncertainty), that is, it treats it as high risk.

## 2. Kiro: Specs and Custom agents (kiro.dev/docs)

**Who and when.** Official Kiro documentation, an AWS product. The pages have no author or date. The HTTP `Last-Modified` (10 Oct 2026) is the site's deployment date, not the writing date. Technical note: the HTML page loads the body with JavaScript, but Kiro publishes a `.md` for each page.

**Phases.** «All specs follow a three-phase workflow»: **Requirements or Bug Analysis → Design → Tasks**, and then Implementation.

**Variants:**

| Variant | What it does |
|---|---|
| **Requirements-First** | requirements → design → tasks |
| **Design-First** | design → requirements; the design can be «High Level Design» or «Low Level Design» |
| **Bugfix Spec** | `bugfix.md` with *Current / Expected / Unchanged Behavior* |
| **Quick Spec** | the three phases «without approval gates» |
| **Plan mode** | read-only; produces a conversational plan, with no formal files |

There is also an optional step, **Analyze Requirements**, that looks for inconsistencies, ambiguities and gaps before design.

**Roles: agents with exact names.**
- *Built-in agents:* **Default**, **Spec**, **Quick Spec**, **Bug Fix**, **Plan**, **Guide** (CLI) and **Help** (CLI, classic).
- *Built-in sub-agents:* **Context gathering** and **General purpose**.
- *Custom agents* are `.kiro/agents/<name>.md|json` files with `tools`, `permissions`, `resources`, `prompt` and `model`. The examples in the documentation: `aws-specialist-agent`, `development-workflow-agent`, `code-review-agent`, `mobile-app-agent`, `domain-finder` and `github-agent`.
- Sub-agents support task DAGs and **review loops** («a reviewer sends work back to an implementer … `NEEDS_CHANGES`», with `max_iterations` between 1 and 10).
- **Human roles:** almost none. «Your role» always addresses a generic user. «product manager» and «engineering team» appear in passing (the «Product Feature Development» pattern), as do «stakeholder buy-in» and «customer». There is no PO, QA or architect as a defined role.

**Artifacts.**
- `.kiro/specs/<name>/` with `requirements.md` (in **EARS** notation: «WHEN [condition/event] THE SYSTEM SHALL [expected behavior]»), or `bugfix.md`, plus `design.md` and `tasks.md`.
- **Steering** (`.kiro/steering/`, with `product.md`, `tech.md` and `structure.md`). The last one covers «file organization, naming conventions, import patterns, and architectural decisions».
- **Hooks** (`.kiro/hooks/*.json`) and **Agent config** (`.kiro/agents/`).

**Human / approval.** Between phases there are «Happy? → Edit/Request changes» checkpoints. Plan mode requires approving the plan before the *handoff*. Quick Spec removes the checkpoints on purpose. At the end, «the agent opens a pull request or merge request». In the CLI, non-interactive sub-agents «can't prompt for approvals».

**After generating code.**
- *Property-based tests* (**Correctness**): Kiro extracts properties from the EARS requirements. It exists only in the IDE and is optional («PBTs are optional by default»). The documentation says: «It provides evidence of correctness, not a proof».
- *Hooks*: `Post Task Execution` («Run tests after a task completes», «Run linting»), `File Save` (linters), and `Pre Tool Use`, which blocks with exit code 2.
- **[Synthesis]** All of this happens **in the agent's session**, not in CI. The specs and agents documentation does not mention CI/CD, pipeline gates, or fitness functions or verifiable architecture rules. Architecture lives in `design.md` and in `structure.md` (steering): it is context for the agent.

**Multi-repo.**
- Kiro Web: «You can add multiple repositories to a single spec session, and the agent plans and coordinates changes across all of them».
- Best practices, specs across teams: «central specs repository», «Git submodules or package references», «Implement cross-repository workflows». And then: «If you have specific needs for cross-project spec management, please share your requirements on our GitHub issue tracker».
- **[Synthesis]** Kiro coordinates the **plan** across repos, but does not say how the cross-repo result is **verified**.

**Useful quotes.**
- «Specs or specifications are structured artifacts that formalize the development process»
- «Requirements are guaranteed to be technically feasible since they're derived from a validated architecture» (Design-First; **[Synthesis]** this is a strong claim with no verification mechanism)
- «Custom agents control **what tools are available and what they can do**. If you want to influence how the agent thinks … use Steering files instead.»
- «While not formal verification, PBT provides evidence for correctness across scenarios you'd never write manually»

## 3. ai-sdlc.io: AI-SDLC Framework

**Who and when.**
- The site **names no company and no author**. It offers a free Community plan (Apache 2.0) and an Enterprise plan («Talk to Sales»).
- Repo: `github.com/ai-sdlc-framework/ai-sdlc`. The organization was created on **7 Feb 2026**, with no company data. Repo description: «Declarative governance framework for AI-augmented software development lifecycles».
- Main contributor according to the GitHub API: `deefactorial` (Dominique Legault), with 1,495 commits.
- Spec **v1alpha1, Status: Draft**. The pages have no publication date.
- **[Synthesis]** It is not an industry standard: it is a young open-source project with a commercial offering. It must be cited as such.

**Phases (home page, exact names).** **1. CAPTURE → 2. DECIDE → 3. ADMIT → 4. DISPATCH → 5. REVIEW → 6. ATTEST → 7. MERGE.** The example Pipeline has the stages `implement`, `review` and `deploy`. The site describes itself as: «Kubernetes for your development process».

**Roles.**
- *Agents in examples:* `coding-agent` / `code-agent` (AgentRole `role: "Software Engineer"` in the Primer and `"Senior Software Engineer"` in the Spec), `reviewer-agent`, `tester-agent` and `deploy-agent`.
- *Cross-harness reviewers:* `code-reviewer`, `test-reviewer` and `security-reviewer`. The DoR evaluator LLM is `refinement-reviewer`.
- *Actors of a Decision:* «Engineering, Product, Design, operator, or framework when LLM-eligible».
- The central human is the **operator**.
- *Personas (Primer §9):* Platform Engineer, Engineering Manager, Security / Compliance Lead, AI/ML Engineer and Software Developer, plus «The Emerging Role: The Agentic Engineer».
- `AutonomyPolicy` contains `requiredApprovals: [engineering-manager]`.

**Artifacts (declarative YAML resources).** `Pipeline`, `Decision`, `AgentRole`, `QualityGate`, `AutonomyPolicy` and `AdapterBinding`, plus `.ai-sdlc/dor.yaml` and DSSE attestations in `.ai-sdlc/attestations/<sha>.dsse.json`. For them, «spec» means the `spec:` section of each resource, Kubernetes style, not a functional spec of the software.

**Human / approval.**
- A **Definition-of-Ready** gate before dispatch. Stage A is deterministic; Stage B is semantic, with an LLM.
- «operator approves» before the merge.
- `AutonomyPolicy` with «Junior…» levels and `requireApproval: all | security-critical-only | architecture-changes-only | none`.
- Routes by complexity: `fully-autonomous`, `ai-with-review`, `ai-assisted` and `human-led`.

**After generating code.**
- Three LLM reviewers in parallel, with **harness independence** («Claude can't review what Claude wrote»).
- A signed attestation that CI verifies: «The CI verifier (`scripts/verify-attestation.mjs`) checks all three are present and approved before allowing merge».
- `QualityGate` with «advisory → soft-mandatory → hard-mandatory» enforcement and rules of type *metric* (coverage), *tool* (`tool`, `maxSeverity`, `rulesets`), *reviewer*, *documentation* and *provenance*.
- **No fitness functions or architecture rules appear.** **[Synthesis]** The *tool-based* rule could host an architecture check, but the source does not propose it. Nor did I find, in what I read, how an «architecture-changes-only» change is detected.

**Multi-repo.** `QualityGate.scope.repositories` accepts globs. «cross-repo» appears only as an Enterprise feature («Enterprise MCP tools (SSO, org policy, cross-repo)»), with no further detail.

**Useful quotes.**
- «turns development into a series of well-framed decisions executed deterministically»
- «The root cause isn't that AI agents write bad code. It's that **nobody orchestrates how they work as the codebase grows.**»
- «correlated reviews are weak reviews»
- «Earned autonomy, not granted» (DP-7)
- Caution: the home page and the Primer cite third-party figures (METR 19% slower, GitClear 7.9% churn, DORA 2024 7.2%, Veracode 45%). These are second-hand data: they must be checked in the primary source before use.

**[Synthesis] Readings of the table:**
1. **No source has a «Scrum Master».** AWS redefines the ritual (bolts, mob) and lets an agent sequence the work (Delivery Agent). If an experiment models a Scrum Master, that is its own addition.
2. Only **aidlc-workflows** separates **producer and reviewer** by discipline (Architect and Architecture Reviewer; Product and Product Lead). ai-sdlc.io separates by **harness** (another model reviews). Anthropic separates by **passes** of the same reviewer.
3. **The human architect almost disappears.** In Anthropic it appears once, as a high-risk approver. In AWS it is a participant in the *mob*. In Kiro and in ai-sdlc.io there is no architect role.

## 5. What no source covers

**[Synthesis]**, with the evidence from each source.

### 5.1 Architecture rules checked in CI (fitness functions)

None of the five sources proposes turning architecture rules (layers, allowed dependencies, module boundaries, contracts) into **deterministic checks that fail the CI pipeline**.
- **Anthropic.** Architecture goes in `CLAUDE.md` («api/ holds REST controllers, core/ holds domain logic…»; «The legacy v1/ package is frozen»). Checking it is left to:
  - in-session hooks: «A skill is an advisory control while a hook is the deterministic layer behind it» (they block protected paths and run the linter);
  - an LLM *Compliance* pass: «the change matches spec.md, plan.md and our design principles».
  - CI appears for tests, lint and evals: «The deterministic checks stay in CI». But it does not propose architecture rules in CI.
- **AWS (blog).** «consistently applying organization-specific standards … design patterns». This is context, with no mechanism.
- **aidlc-workflows.** Its CI quality gates are lint, coverage, security, integration, manual approval and smoke. Architecture is reviewed by an **LLM agent** (Architecture Reviewer).
- **Kiro.** Architecture lives in `design.md` and `structure.md`; both are context. What is deterministic sits in hooks inside the session (lint, tests, Pre Tool Use) and in PBT of functional behavior. It does not mention CI.
- **ai-sdlc.io.** It has the richest gate machinery (graded enforcement, *tool-based rules*, attestations verified in CI), but the example gates are coverage, security, reviewers and provenance. None is about architecture.
- **Common pattern:** all of them put architecture **before** generating (context or LLM review). None puts it **after**, as a deterministic check in CI. This is exactly the gap between the «two moments of verification».

### 5.2 Changes that cross repositories

- **Kiro** is the only one that **plans** across repos (Kiro Web, several repos in one spec session). To share specs between teams it offers only *submodules* and «cross-repository workflows», and asks for feedback on GitHub. It does not say how a cross-repo change is verified.
- **Anthropic** only says that «A dedicated intent repo is only worth the overhead when intent spans many repositories». The other pieces (CLAUDE.md, hooks, review) are per repository.
- **aidlc-workflows** is the only one that mentions a check across repos: «Use contract testing (Pact) to verify compatibility across repos». It does so as a knowledge pattern for the agent, not as a mandatory gate. And it treats multi-repo as high uncertainty.
- **ai-sdlc.io**: `scope.repositories` with globs, and «cross-repo» only as an Enterprise feature, with no detail.
- **AWS (blog)**: nothing.
- **Nobody covers:** how an architecture rule that lives in one repo (or in a central spec) is enforced in the consuming repos, or how to coordinate the merge order and the checking of a change that touches several services. **[Synthesis]** For the experiment: consumer contracts and dependency rules in each repo's CI fill a space these sources leave empty. It is a defensible contribution of its own, as long as it is presented as a field report and not as a universal finding.
